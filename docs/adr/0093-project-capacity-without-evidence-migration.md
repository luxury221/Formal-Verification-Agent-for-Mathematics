# ADR 0093 — 可逆项目归档与旧证明身份隔离

- 日期：2026-10-30
- 状态：采用；验收见 `artifacts/project-capacity-20261030-01/`

## 问题

正式研究库已有100个项目，旧 `ResearchStore.create` 按物理记录数限制创建。论文后续 Studio 任务因此无法建立，上轮只能复用旧项目容器。删除历史、直接扩大旧验证器配额或原地修改参与历史证明身份的 `research.py` 均不适合解决这个问题。

## 决策

新增 `ManagedResearchStore` 继承旧存储。HTTP、Studio 创建及新运维 CLI 使用新类；数学执行器继续按原实现读取原项目记录。原 `research.py`、旧 Lean 模板、执行器和封存工具树保持字节不变。

同一个 SQLite 数据库增加 `research_capacity_identity`、`research_project_lifecycle`、`research_lifecycle_requests`。身份为 `research-project-capacity-v1`。旧项目没有生命周期行时视为 ACTIVE、revision 0。归档只改变组织状态，不修改原项目正文、版本、分支、证据绑定或数学结论。

- 活跃项目上限100，包含归档的保留项目上限10000，生命周期请求总上限50000。
- 归档释放一个活跃名额；不释放保留记录额度，也不回收证明存储。
- 恢复和创建使用同一库的 `BEGIN IMMEDIATE` 事务检查全局活跃配额，避免并发超配。
- 归档不是只读锁。已有项目、笔记和验证器仍可通过直链访问或继续工作；工作进程资源限制另行管理。
- 默认 `/v1/research` 列表只显示 ACTIVE。容量目录列出两种状态；Studio 列表仍保留已有笔记入口。

写请求要求精确字段、整数修订、操作人、原因和字面 `true` 确认，沿用同源/CSRF保护。同编号同内容重发只返回当前生命周期状态；如果其后已经恢复，旧归档请求不能再次归档。陈旧修订、不同内容复用编号、满额恢复和 SQL 失败不提交新状态。正文快照、项目写入和创建请求也保持原子性。

生命周期正文有摘要，修订须与请求行计数和最大修订相符。部分表缺失、身份变化、缺失生命周期但仍有请求历史、悬空引用和摘要变化会拒绝读取。它不是抵抗整库替换的外部签名系统，不宣称可以检测攻击者同时重写全部数据库和备份。

## 历史与回滚

升级前以 SQLite backup API 保存一致快照及原100个项目、原请求/修订、源码和证明工件摘要。初始化新表不迁移或重算旧数学证据。专项测试验证旧类仍可读归档前后的相同项目正文，以及新类创建的原格式项目。

回滚代码时必须保留当前完整数据库和新表。旧程序不理解归档状态，会按旧列表语义显示项目；旧创建仍受物理100条限制，旧 Studio 超过其原笔记上限时也可能拒绝列出。可读性兼容不等于旧版本具备新容量功能。

**新版本产生任何新记录后，不得用升级前整库备份直接覆盖当前库。** 这会丢失新研究和请求。故障恢复应先停止写入、保存当前一致快照、核对差异，再针对明确故障恢复；不能靠删除生命周期表“重置”归档。旧证明损坏仍由各自验证器处理，归档不会恢复失效证明。

## 代价与边界

容量清单目前逐项读取并校验项目正文，尚无10000项目规模的时延、内存和并发性能证据。10000是保留策略上限，不是已经实测的高效运行规模。归档也不降低旧证明工件的磁盘占用。

请求历史保存编号、项目、修订和请求摘要；生命周期行保存最新操作人和原因。它支持幂等与修订一致性检查，但不保存每次旧操作的完整原因正文，不称为完整操作审计日志。需要更完整历史时应通过明确的新协议演进。

界面有搜索、状态筛选、可逆确认、错误保留请求编号和草稿保护。归档后的列表刷新遇到未保存研究图时保留草稿并提示，用户另行保存或明确刷新页面。容量面板需手动刷新才能反映其他窗口的操作。

## 验收

相关191项测试通过，含17项新增容量测试和原13项研究协议；格式调整保持 AST 一致，17项专项复验通过。另有16条实际 CLI、7项实际浏览器交互及3项只读视觉检查。保留初次格式检查和全部实际负向请求结果。

正式服务从100 ACTIVE / 100保留变为100 ACTIVE / 1 ARCHIVED / 101保留。归档的是确认为无节点、无绑定的旧界面测试项目，新增的是论文 Proposition 2 的完整原题研究任务。原100个项目正文/摘要逐字不变。论文仍未完成，新增任务 UNKNOWN，未请求模型或新数学验证。旧证据有效性及最终摘要以 `verification.json` 为准。
