## 推荐的参赛闭环

工作流目标：原文片段 → 命题与假设提取 → Mathlib 检索 → 受控形式化候选 → 人工语义确认 → Lean 检查与独立回放 → 带原文定位的审计报告。

openJiuwen 负责实际工作流编排、任务状态和工具调用；项目现有内核负责形式化输入门禁、精确目标、公理审计和证据有效性。工作流不得绕过原审核和验证边界，也不得仅在界面添加品牌而宣称已经深度集成。具体 SDK 组件和版本须接入前核对官方文档、许可与当前工具链兼容性。

初赛材料可以诚实展示已实现基础与计划架构，无需为创意申报提前声称模型效果。后续若演示自主提取、规划或修复，须接入真实模型，保存真实运行轨迹，并明确区分模型生成、人工修改和参考样例。

三分钟演示建议只做一个短闭环：展示原文局部目标和条件，运行检查，回到原文显示证据及剩余义务。正确证明、错误证明被拒、经正式验证的限定反例可作为三类样例；候选被拒不能直接标为数学命题被否定。耗时部分可以剪辑，但必须标注实际时间、人工参与和历史记录，不能将回放录像伪装为实时自主输出。

Hölder 例子只有在 v4 修复、回归、正式核验及原文对齐回收完成后才列入正式成果。完成前使用既有验收成功的局部定理，并保留未完成状态。

## 初赛 PPT 建议结构

1. 作品名称与一句话价值：让数学论证的核查结果附带可重放证据。
2. 用户与问题：科研阅读和写作中，遗漏条件与局部推理错误难以系统追溯。
3. 使用过程：从原文选中命题，到核验结果定位回原文。
4. 架构：智能体编排、检索、形式化、Lean、独立回放、证据账本；图中区分已实现与拟新增。
5. 技术创新：语义对齐与内核检查分离、局部义务依赖图、失效传播和原文回溯。
6. 可行性证据：既有真实 Lean 工件及论文局部成果；明确并非全文覆盖或模型求解率。
7. 本次新增与计划：openJiuwen 实际适配、可复现实例、审计报告；标明依赖与贡献边界。
8. 演示与评估：目标闭环、真实用时和失败状态；不写未经实测的提效百分比或获奖预测。
